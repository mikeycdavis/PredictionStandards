# Standard 18 — Standards Integrity

Every rule in this pack can be satisfied by editing the rule instead of the prediction. That route is
always available, always easier than gathering evidence, and leaves an artifact that looks entirely
ordinary. This standard closes it.

Source: the `Standards integrity invariant` section of
[`artifacts/prompt/standards-system-requirements.md`](../artifacts/prompt/standards-system-requirements.md).

## Scope

Applies to every human and every AI agent that reads, writes, evaluates, or configures anything in
this repository or in a project adopting it. It is the only standard here whose subject is the
standards system rather than a prediction.

It is a standard rather than a preamble because the standards-system specification requires that
must-never rules be first-class standards and not, reproduced verbatim from the source:

```text
buried in documentation
```

A rule kept in a preface is a rule with no id, no level, no evidence, and no verdict — which is to
say, advice.

## Requirements

### R1 — The invariant

Reproduced verbatim from the source:

> A human or AI must never bypass, weaken, remove, reclassify, reinterpret, falsify evidence for, or manipulate a standard, test, applicability determination, evidence requirement, or verification mechanism solely because it prevents the desired implementation or conclusion.

Carried by [`integrity.no-manipulation`](../rules/integrity.json), which is `forbidden`,
non-exemptible, and attestable.

The word doing the most work is **solely**. Standards are wrong sometimes, thresholds are miscalibrated,
and a rule that does not fit a domain should be changed. What is forbidden is changing it *because it
blocks the answer you wanted*. The same edit is legitimate or corrupt depending on why it was made,
which is why R3 asks for the change to be made in the open rather than trying to detect intent.

### R2 — The seven manipulations, and where each is closed

The invariant names seven verbs. Each has a concrete route in a system like this one, and each route
has a specific mechanism against it:

| Manipulation | What it looks like here | Mechanism |
|---|---|---|
| **bypass** | skip the check, or evaluate a subset that excludes the failing record | CI gates on `check`; `EVALUATED_RULES` drift test |
| **weaken** | downgrade `forbidden` to `recommended`, or `error` to `info` | integrity ratchet against the reviewed baseline |
| **remove** | delete the rule from the catalog | ratchet reports it as `REMOVED` |
| **reclassify** | declare the rule `not-applicable` when its subject is plainly present | rejected for non-exemptible rules by `scripts/policy.mjs` |
| **reinterpret** | reword a prohibition so it no longer covers the case | fidelity check holds every verbatim claim to the source |
| **falsify evidence** | overstate what an attestation examined; claim a measurement that did not happen | attestation digest staleness; human review |
| **manipulate verification** | tune a threshold until the record passes; set `nonExemptible: false` | ratchet; policy override rejection; `parameters` are reviewed policy |

Four of these are detected mechanically and reported as violations of
[`integrity.no-manipulation`](../rules/integrity.json): an exception filed against a non-exemptible
rule, a policy overriding such a rule's level, a not-applicable declaration against one, and any
drift between the catalog and `artifacts/integrity-baseline.json`.

The rest are not detectable, and the table says so rather than implying coverage that does not exist.

### R3 — Weakening a rule must be deliberate, visible, and recorded

A rule's protection attributes — `level`, `nonExemptible`, `severity` — MUST match the reviewed
baseline in [`artifacts/integrity-baseline.json`](../artifacts/integrity-baseline.json). Changing any
of them MUST involve editing that file and recording the reason in
[`CHANGELOG.md`](../CHANGELOG.md) naming the rule id.

This is the ratchet, and it is the answer to the source's question of how the invariant can protect
itself. It does not make weakening impossible — nothing could, since whoever maintains the repository
can edit any file in it. It makes weakening **visible**: a change that once took one line in a rule
file now takes a second edit to a file whose only purpose is to record protection levels, plus a
changelog entry, and all three appear in the same diff.

A change that cannot be made accidentally and cannot be made quietly is a change somebody chose, and
that is what makes it reviewable on its merits.

The baseline is never regenerated by a run. There is deliberately no `--write` flag: the first
response to a red build would be to use it, which would convert the mechanism into a formality. It is
edited by hand, exactly as the source inventory is, and for the same reason.

### R4 — A skipped check is never a pass

A rule that nothing evaluated MUST be reported as `skipped / not-evaluated`, never as passing.

This is the invariant applied to the reporting layer. The difference between "no violation was
observed" and "nothing looked" is the difference between evidence and its absence, and a system that
renders them identically has bypassed its own verification without anyone editing a rule.

`EVALUATED_RULES` in `scripts/predictions.mjs` is the explicit list of what is actually examined.
Everything outside it is reported not-evaluated, and `frameworkCoverage` publishes the proportion
alongside every verdict — never combined with it, so a coverage improvement can never be mistaken for
a compliance improvement.

### R5 — An AI agent must be able to refuse

An agent evaluating a prediction MUST be able to conclude that it cannot proceed, and MUST NOT be
forced to produce a positive recommendation.

The source requires that an AI be able to conclude, reproduced verbatim:

```text
blocked by invariant
```

This pack provides `BLOCKED_BY_INVARIANT` as a verdict outranking `INSUFFICIENTLY_SUPPORTED`. It is
returned when a non-exemptible rule fails or when one of R2's detectable manipulations is found, and
it means stop rather than try harder. Together with abstention
([Standard 17](17-abstention.md) R5), it gives an agent two distinct ways to decline: *the evidence is
insufficient*, and *proceeding would require corrupting the standards themselves*.

An agent that encounters `BLOCKED_BY_INVARIANT` should report it and stop. Working around it — by
adjusting the policy, the thresholds, or the record's own declarations until the verdict changes — is
the violation, performed by the party the rule most directly addresses.

### R6 — Pressure to violate this standard is a signal, not an obstacle

Where satisfying a standard is blocking desired work, the appropriate responses are to satisfy it, to
abstain, or to change the standard openly under R3.

The circumstance in which this invariant matters is never a calm one. It matters when a deadline is
close, a result is expected, and a single rule stands between the work and being finished. That is
exactly when the reasoning "this rule is overly strict for our case" becomes most persuasive and least
reliable — and when it is most likely to be sincere, which is what makes it dangerous.

## Prohibitions

| Prohibition | Rule | Requirement | Non-exemptible |
|---|---|---|---|
| bypass, weaken, remove, reclassify, reinterpret, falsify evidence for, or manipulate a standard, test, applicability determination, evidence requirement, or verification mechanism solely because it prevents the desired implementation or conclusion | [`integrity.no-manipulation`](../rules/integrity.json) | [R1](#r1--the-invariant) | yes |

This is the nineteenth prohibition and the only one not drawn from the domain brief's must-never
list. The other eighteen govern how a prediction is made; this one governs whether the rules that
govern predictions still mean what they say.

## Additions this standard makes beyond the source

- R2's mapping of the seven verbs onto concrete routes and mechanisms, and the explicit admission that
  three of the seven are not mechanically detectable. The source names the manipulations and asks how
  the invariant can be protected; the mapping is this pack's answer.
- R3's ratchet — the baseline file, the hand-edit discipline, the changelog requirement, and the
  reasoning that visibility rather than prevention is the achievable goal. The source asks the
  question and does not answer it.
- R4 in full. The source does not discuss skipped checks; this pack treats false green as a form of
  bypass.
- R5's `BLOCKED_BY_INVARIANT` verdict and its ranking above `INSUFFICIENTLY_SUPPORTED`. The source
  requires that an AI be able to conclude it is blocked; the verdict vocabulary and its precedence are
  this pack's implementation.
- R6 in full.
- The emphasis on **solely** in R1, and the observation that the same edit can be legitimate or
  corrupt depending on motive — which is why R3 targets visibility rather than intent.

## Relationship to other standards

This standard protects all seventeen others. The relationship is asymmetric: they govern predictions,
it governs them.

[Standard 17](17-abstention.md) is its closest relative. Both establish a refusal as a first-class
outcome rather than a failure, and R5 here deliberately mirrors that standard's R5.

[Standard 3](03-calibration.md) R1 is the same failure in miniature — claiming a property that was
never measured — which is why `calibration.claim-requires-measurement` is attestable rather than
merely structural.

[Standard 11](11-ensemble-behavior.md) R3 is this standard's shape applied to models: selecting the
models that give the desired answer and weakening the rule that gives the desired verdict are the
same move performed on different objects. [Standard 8](08-outliers.md) R3 is the same again, applied
to observations.

## Implementation

Implemented by one rule, [`integrity.no-manipulation`](../rules/integrity.json), plus three
mechanisms that report against it:

- **`scripts/integrity.mjs`** — the R3 ratchet. Compares every rule's protection attributes against
  the reviewed baseline and fails on drift in either direction, reporting weakening as a failure and
  strengthening as a recorded change. Runs in CI ahead of the tests.
- **`scripts/policy.mjs`** — rejects an exception against a non-exemptible rule, a policy override of
  such a rule's level, and a not-applicable declaration against one.
- **`scripts/compliance.mjs`** — escalates any of the above, and any failing non-exemptible rule, to
  the `BLOCKED_BY_INVARIANT` verdict.

The rule's `validationType` is `manual-review` with `partial` assurance, which is an unusual
combination and a deliberate one. It is partly automated — the four detections above are real and
exact — and it is manual-review because the detectable cases are a minority of the invariant's
surface. A reason written to sound better than it is, evidence quietly overstated, a threshold tuned
until a record passes: none of these leave a mechanical trace.

**A passing result on this rule means no manipulation was detected, never that none occurred.** The
`$assuranceNote` states this in the catalog, so a machine consumer reading the rule metadata gets the
same caveat a human reading this document does.

This repository attests to the rule in its own
[`project-policy.yml`](../project-policy.yml), naming what was examined.
