# PredictionStandards

## Purpose

Determine whether an individual prediction is sufficiently supported by the information legitimately
available when it was made. Provide a structured, auditable, testable system for that question, with
abstention and refusal as first-class outcomes.

Explicitly **not** a machine-learning standard: nothing here evaluates a model. See
[docs/ml-vs-prediction-boundary.md](docs/ml-vs-prediction-boundary.md).

## Standards

Version 1.0.0. 18 standards, 50 rules, 19 prohibitions of which 9 are non-exemptible. Written from
two committed sources: the domain brief (`artifacts/prompt/original-prompt.md`, standards 1–17) and
the standards-system requirements (`artifacts/prompt/standards-system-requirements.md`, standard 18).

This repository is its own first adopter: [project-policy.yml](project-policy.yml) governs the
example records, and CI evaluates them on every run.

## Stack

Node.js ≥ 18, ESM, **zero third-party dependencies**. Tests run on `node --test`. The YAML and JSON
Schema evaluators are hand-written strict subsets that throw on anything they do not understand,
rather than guessing.

## Commands

| Command | What it does |
|---|---|
| `npm run inventory` | the committed enumeration still matches the sources |
| `npm run fidelity` | every "reproduced verbatim" claim actually is |
| `npm run integrity` | no rule's protection drifted from the reviewed baseline |
| `npm run policy` | this repository's own policy is valid |
| `npm run diagrams` | the architecture diagram matches its Mermaid source |
| `npm test` | the full suite |
| `npm run audit` | survey the example records; no verdict |
| `npm run check` | evaluate the example records; the authoritative verdict |

CI runs all eight, in that order.

## Environments

None. This repository is documents, a CLI, and its tests. It reads files, writes nothing outside a
target project during `init`, and makes no network calls.

## Integrations

None. No third-party packages, no services, no telemetry. CI has no install step, so introducing a
dependency breaks the build by design.

## Architectural rules

1. **Three-way separation.** The catalog defines rule identity and metadata; `project-policy.yml`
   defines project applicability; the evaluator produces evidence. None may redefine the others.
   `assertBindings` enforces the evaluator's half mechanically.
2. **A rule nothing evaluated is `skipped`, never `passed`.** `EVALUATED_RULES` is the explicit
   boundary, and a test asserts it agrees with the detectors.
3. **Manual-review rules never pass automatically.** Only a valid, unexpired, digest-fresh
   attestation establishes them.
4. **Status is computed from rules, never from the score.** No percentage grants support.
5. **Framework coverage never combines with the verdict.** A tooling improvement must not look like
   a support improvement.
6. **A malformed policy or unreadable record is exit 2 / `NOT_EVALUATED`,** never a failing verdict.
7. **`audit` and `check` are separate commands with different exit contracts.** No flag moves one
   into the other.
8. **Non-exemptible rules cannot be waived by any route** — exception, level override, or
   applicability declaration. Each attempt is reported as an integrity violation.
9. **The reviewed inventory and the integrity baseline are never regenerated by a run.** Both are
   hand-edited, and there is deliberately no `--write` flag.
10. **Evaluation is deterministic given `--as-of`.** Nothing reads the wall clock.
11. **Probability, confidence, edge, and expected value are structurally distinct.** Conflating them
    is a schema error rather than a matter of remembering.
12. **Do not paraphrase source text.** Quote it verbatim, or mark it as authored. The fidelity check
    holds every verbatim claim to its word.
13. **State what a check does not establish.** Every rule with less than full assurance carries a
    `$assuranceNote`, and a test enforces it.

## Current state

Version 1.0.0, complete against both source specifications, and **the architecture is frozen as the
v1.0 baseline.** 46 of 50 rules have a detector; 16 of 18 standards are fully machine-represented.
The four unevaluated rules are the three outcome-bias and lookahead-evaluation rules — which concern
reasoning about resolved predictions, where no artifact exists to inspect — and
`integrity.no-manipulation`, which is partly automated. All four are reported `not-evaluated` until
attested, never as passes.

Coverage of 46/50 is a designed boundary, not unfinished work. Do not add detectors to reach 50/50;
see [CHANGELOG.md](CHANGELOG.md). New rules should come from real adoption exposing a missing rule, a
false positive, a false negative, or a badly calibrated threshold — not from speculative expansion.

Known limits are enumerated in [INSTRUCTIONS.md](INSTRUCTIONS.md) §9 and in each rule's
`$assuranceNote`.
