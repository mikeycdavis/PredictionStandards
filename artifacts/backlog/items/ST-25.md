## What

Submit the verified candidate through the guarded path, require hosted CI on that exact head, merge
without replacing the commit object, re-run all eight gates from `main`, then tag and push.

## Why

ST-13's rule, applied again: verification has to run from the commit that will actually be tagged.

## Notes

Ancestry and tree identity were measured **separately** after the merge rather than inferred from
each other. Both held — `3b89e20` is an ancestor of `898347a`, and the trees are identical — so the
strong claim was available without narrowing it.

Hosted CI's first attempt on `75d1840` reported `failure` having executed **zero steps**: an account
billing condition refused the job before any step ran. That is `NOT_EVALUATED`, not a red, and the
release held rather than reinterpreting it or weakening the gate. The rerun on the same SHA
executed and passed.

Verification at the tagged commit: host 8/8, container 8/8, 274 of 274 tests executed with none
skipped, and hosted run 32881404396 successful on the same SHA. The published tag object hashes
identically local and remote, so the annotated message is the approved one rather than an
equivalent target.
